### 3.2. Замечания по требованиям

#### R-01 · строка 29

> Карты → Расходы → Уведомления. На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить».

**🟡 F-001 · Незначительно · Полнота**

- Место: строка 29 — «На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить».»

## 6. Итог

- **Можно ли начинать разработку:** Нет
- **Можно ли начинать тестирование (проектирование тестов):** Нет

Документация содержит критические противоречия в бизнес-логике и архитектуре API (F-006, F-008, F-015, F-019, F-022, F-029), блокирующие разработку и тестирование. Логика определения месяца (F-006) и лимитов push-уведомлений (F-008) некорректна, а денежные единицы (тиыны и тенге) не имеют алгоритма приведения (F-029). Кроме того, API не содержит метода для чтения настроек (F-015) и использует метод GET для мутации данных (F-018).

Правило решения: есть хотя бы одно критичное нарушение — «Нет»; есть только существенные — «С оговорками». Модель не может ослабить это решение.

### Что исправить в первую очередь

1. Устранить критические противоречия в бизнес-логике: расчет месяца покупки, ограничение на количество push в месяц и конвертация тиынов в тенге. (F-006, F-008, F-029)
2. Доработать спецификацию REST API: добавить метод чтения настроек, заменить GET на POST/PUT для сохранения и исправить статусы ответов об ошибках. (F-015, F-018, F-019, F-022)
3. Устранить несогласованность типов данных (amount, enabled) и описать схемы параметров запросов и ответов. (F-021, F-023, F-024, F-025, F-026)
4. Уточнить бизнес-сценарии: обработать статус enabled при проверке push и описать поведение при изменении лимита выше текущих расходов. (F-003, F-009, F-010, F-014)
5. Заполнить пропущенные метаданные документа, разделы тестирования, чек-лист ревью и параметры сред. (F-031, F-032, F-033, F-034, F-035, F-036)
