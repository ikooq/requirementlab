# RequirementLab — текст для подачи

**Репозиторий:** https://github.com/ikooq/requirementlab/tree/audit-work
**Отчёт агента:** `reports/report.md` (и `reports/report.json`), приложен к подаче
**Проверяемый документ:** `docs/requirements.md` из репозитория организаторов, приложен к подаче

## Коротко (1–2 предложения)

RequirementLab — AI-агент статического ревью требований по ISO/IEC/IEEE 29148 и IEEE 830. Он нарезает документ на требования, проверяет каждое и весь набор, а затем пишет отчёт на русском, где каждое нарушение подтверждено дословной цитатой с номером строки.

## Что получилось на документе кейса

- Отчёт сформирован версией агента `v1.3.0` на `gemini-3.5-flash` (2 прохода); все цифры этого раздела относятся к нему. Свежий прогон текущего кода на запасной `gemini-3.5-flash-lite` в один проход нашёл 17 из 41 и 3 из 6 критичных; штатный прогон текущего кода на `gemini-3.5-flash` ещё не измерен.
- 27 требований, 40 нарушений, из них 4 критичных. Итог: разработку и тестирование начинать нельзя.
- Найдены все ключевые противоречия: Ф-3 и Ф-4 (лимит push), AC-2 и Ф-2 (месяц покупки), цель «в момент покупки» против учёта только проведённых покупок, суммы в тиынах против порога в тенге, сохранение через GET, ответ 200 с `ERROR` вместо 400, типы `amount`/`enabled` в запросе и ответе, 403/404, отсутствующий метод чтения настроек.
- Качество измерено: мы собрали эталон из 41 дефекта кейса, и отчёт находит 37 из 41 (90%) и все 6 критичных. 35 дефектов эталона составлены вручную до прогонов агента, по ним результат 31 из 35 (89%); ещё 6 — находки агента, которых не было в эталоне и которые подтвердились при проверке по документу.
- Проверено вслепую: мы написали второе ТЗ (автоплатёж за мобильную связь) с 30 заложенными дефектами и закоммитили эталон до первого прогона. За один проход агент нашёл все 5 критичных противоречий и 22 из 30 дефектов (73%) по скрипту, 24 из 30 (80%) по ручной сверке. После публикации первого результата этот документ использовался для регрессий. Скрипт оценки лежит в репозитории (`eval/score.py`).

## Чем решение отличается

1. **Проверяемые цитаты.** Агент сам находит каждую цитату модели в документе и вычисляет строку. Находки, для которых цитата не нашлась, в отчёт не попадают, а показываются в приложении с причиной отсева.
2. **Детерминированный итог.** Решение «можно ли начинать» принимает правило, а не модель: есть критичное нарушение — «нет».
3. **Второй ревьюер.** Отдельный проход модели снимает ложные срабатывания и дубли и перепроверяет каждое «не определено» по всему документу.
4. **Два независимых прохода.** Модель от прогона к прогону ловит немного разные дефекты; агент проверяет документ дважды и объединяет находки: 89% против 80% у одного прохода (по 35 дефектам, собранным до прогонов).
5. **Правила без LLM.** Заглушки, пустые таблицы, незаполненный чек-лист, отсутствие версии находятся детерминированно.
6. **Любой формат.** MD, TXT, PDF и DOCX; таблицы PDF восстанавливаются целиком, включая пустые ячейки.
7. **Надёжность на бесплатном тарифе.** Несколько ключей, запасные модели, кэш ответов; перегрузку сервера агент пережидает.

## Как проверить сдаваемый отчёт

Комплект содержит результаты анализа версии `v1.3.0`. Чтобы проверить цитаты и регрессионные метрики без ключа и без обращения к модели, в чистой копии выполните:

```bash
git clone --branch audit-work https://github.com/ikooq/requirementlab
cd requirementlab
python -m pip install -r requirements.txt
curl -fL --create-dirs -o docs/requirements.md https://raw.githubusercontent.com/BCC-HUB/ai-requirements-validator-task/928c1aa364265426105b69ba7a3444eac11b22db/docs/requirements.md
python -m eval.evidence docs/requirements.md reports/report.json
python -m eval.promotion gate reports/report.json eval/promotion-review.csv
```

Ожидаемый результат для этого комплекта — 70 подтверждённых цитат, 37/41 дефектов эталона и 6/6 критичных. Внутренняя точность 95% получена по 38 автоматическим совпадениям с командным эталоном и двум ранее отмеченным дублям.

## Как повторить анализ той же версией агента

В той же чистой копии переключитесь на тег генератора. Впишите ключ Gemini в локальный файл `.env`. В PowerShell вместо `cp` можно использовать `Copy-Item`.

```bash
git checkout v1.3.0
python -m pip install -r requirements.txt
cp .env.example .env
python run.py docs/requirements.md reports/replay-v130.md --model gemini-3.5-flash --passes 2 --batch-size 6 --no-cache
```

Команда запускает штатную конфигурацию тега и сохраняет новый отчёт отдельно. Опубликованный JSON v1.3.0 не записывал размер пакета и число проходов; его паспорт сообщает о 18 ответах из кэша. При новом обращении к API состав находок может измениться. Проверяйте фактически ответившую модель. Для ориентира, в отдельном прогоне на коде d2b3fe9 после исчерпания квоты все ответы дала gemini-3.5-flash-lite: один проход пакетами по 12 дал 17/41 и 3/6 критичных. Влияние одной только замены модели этим опытом не измерено.

## Скачать комплект подачи

В GitHub откройте Actions → tests, выберите успешный прогон ветки `audit-work` и скачайте архив `requirementlab-submission-<коммит>` в разделе Artifacts. В нём исходный документ организаторов, полный и краткий отчёты агента, JSON, оценка по эталону и этот текст. Хеш в имени архива указывает ревизию сборки. Версия агента, создавшая сам отчёт, записана в его паспорте.
